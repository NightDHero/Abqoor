# Media System Specification

## Purpose

Define how Abqoor stores and serves question images, source PDFs, and importer media.

## Source Of Truth

- Media binaries are not stored in the structured database.
- Production permanent media is stored in private Cloudflare R2 through the backend storage abstraction.
- Local filesystem media is for local development, test runs, migration/backfill input, and temporary processing only.
- Browser clients never receive R2 credentials, storage keys, or direct R2 object URLs.
- Question images remain accessible through the application route `/question-images/:fileName`.
- Original source PDFs are protected admin assets and are only available through authenticated admin routes.

## Storage Drivers

The backend selects one storage driver through `STORAGE_DRIVER`:

```text
local
r2
```

Development defaults to `local`. Production defaults to `r2` and requires R2 credentials.

`R2_PUBLIC_BASE_URL` is intentionally optional and unused by the current private-bucket architecture.

## Object Key Structure

Question images:

```text
questions/{questionId}/question.webp
```

Original source PDFs:

```text
pdfs/originals/{sourcePdfId}/original.pdf
```

Import staging and backups:

```text
imports/{importJobId}/...
```

Object keys are generated by backend code. Uploaded filenames, route filenames, and user input must never be trusted as storage keys.

## Public Image Contract

Student-facing question records use the existing image route:

```text
/question-images/Q-065.webp
```

The route looks up the canonical question record and reads `questions.image_storage_key` when present. In local development, legacy local images may still be served as a compatibility fallback. In production, missing database records or missing stored objects return `404` rather than reading arbitrary local paths.

The current cache policy is:

```text
public, max-age=300
```

This intentionally avoids long immutable caching because admin imports can replace question images.

## Import Flow

The admin importer performs:

```text
upload PDF
-> store original PDF object
-> create source_pdfs metadata
-> render pages to temporary PNG files
-> optimize each page to WebP
-> stage WebP objects
-> validate Excel/PDF mapping
-> confirm import
-> promote staged objects to final question keys
-> write question records with image_storage_key, source_pdf_id, and source_page
```

Temporary render files must be cleaned up after successful and handled failed processing. Permanent production data is PostgreSQL metadata plus R2 objects.

## Source PDFs

The `source_pdfs` table records:

- source PDF id
- original filename
- storage key
- upload timestamp
- file size
- page count
- status
- creating administrator

Admin source-PDF retrieval must require admin authorization and must read through the storage abstraction.

## Backfill

`npm run storage:backfill-images -w apps/api` migrates existing local question images into the configured object storage.

The backfill is designed to be:

- idempotent
- resumable
- non-destructive
- per-row failure tolerant
- verified before database updates

It does not delete local source images. Do not run it against production until R2 smoke testing and a small new import have passed.

## R2 Smoke Test

`npm run storage:smoke-r2 -w apps/api` is the explicit credentials/configuration test for R2. It writes, reads, copies, deletes, and verifies one temporary object under a generated smoke-test prefix. It must never touch application objects or print secrets.

## Access Control

- Admins can upload and retrieve source PDFs through admin routes.
- Students can view question images only through `/question-images/...`.
- Students cannot write media or access original source PDFs.
- R2 remains private.

## Non-Goals

- No public R2 bucket.
- No browser-side R2 credentials.
- No binary media in PostgreSQL or SQLite.
- No AI image interpretation.
- No video handling in the current MVP.
